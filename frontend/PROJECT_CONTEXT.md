## 2. Постановка и ожидаемый результат

Формулировка кейса, переданная участником команды.

> Разработать систему мониторинга городской инфраструктуры МГТС с применением компьютерного зрения. На основе изображений, полученных с камер служебных автомобилей, система должна распознавать объекты инфраструктуры (кабельные колодцы, опоры и др.), определять признаки неудовлетворительного состояния и формировать перечень объектов, требующих проверки или ремонта, с привязкой к местоположению.

Рабочий вопрос оператора — где находится проблемный объект, какой признак обнаружен и на каком фото это можно увидеть. Практическая ценность — сократить объём ручного просмотра кадров и дать сотруднику перечень адресных проверок. Это ожидаемый эффект. Его величину определяют только после замера на контрольных данных.

| Часть задачи | Смысл |
| --- | --- |
| Распознавание объекта | Определить, что за объект виден на кадре, и по возможности показать его область. Например, в кадре видна крышка кабельного колодца. |
| Определение состояния | Выделить видимый признак возможного дефекта и связать его с объектом. Фото может дать основания для осмотра, а решение о подтверждении состояния принимает сотрудник в рамках согласованного процесса. |
| Привязка к месту | Соотнести результат с фактической или ориентировочной точкой, указать источник локации и сохранить связь с кадром. Координата камеры и координата объекта могут различаться. |
| Выход системы | Перечень кандидатов на проверку или ремонт с типом объекта, признаком проблемы и локацией. Фото или кадр позволяют человеку перепроверить конкретную запись. |

Кабельный колодец — объект инфраструктуры, его крышка может быть видимой частью на фото. Командное слово «люк» может быть меткой на изображении, UI-ярлыком или отдельным классом модели. До разметки определить, какое значение используется. Опоры тоже указаны в постановке как пример. В командной таблице упоминаются просадки покрытия. Принадлежность таких просадок к кейсу, их связь с колодцем и официальный каталог дефектов требуют уточнения. Например, «смещение крышки» или «видимый наклон опоры» можно использовать в демонстрационном обсуждении как гипотезы классов при наличии подходящих кадров.

## 3. Объём MVP и сценарии пользователя

**План команды.** Авторизация с JWT, адаптивный веб-интерфейс с вкладками, пакетная загрузка фото и видео, фоновая обработка, выдача объектов и дефектов, интерактивная карта дефектов, фильтр по критичности, отчёт CSV/XLSX и локальный запуск через Docker Compose. Постановка требует обработки изображений. Обработка видео расширяет этот сценарий через извлечение кадров.

**Выбранная для описания роль.** Оператор мониторинга или инженер МГТС. В MVP это может быть один демопользователь. Какие роли и права нужны для реальной эксплуатации, в материалах не определено. Ремонтная бригада может быть получателем выгрузки, если команда подтвердит такой процесс.

1. Оператор входит в систему и открывает раздел загрузок.
2. Выбирает пакет фото, а после подключения видео — также видеозаписи. Передаёт геоданные предусмотренным способом, если они доступны отдельно.
3. Система принимает материалы. Оператор видит, какие файлы сохранены и какой статус обработки у каждого.
4. Воркер запускает распознавание. Для каждого успешно обработанного кадра сохраняется результат, включая случай с нулём детекций.
5. Оператор открывает список, видит объект, видимый признак, фото, статус и доступное местоположение. При необходимости сужает выборку до объектов, требующих внимания.
6. Объекты с пригодной для отображения локацией показываются на карте. Оператор открывает исходное наблюдение по метке и выгружает строки отчёта.
7. Результаты, где локация неизвестна, остаются доступны в списке с понятной пометкой. Сбой обработки виден отдельно от результата без детекций.

**Предлагаемый порядок сборки.** Сначала довести один сквозной проход на фото с известной локацией. Затем добавить пакетные и отрицательные случаи, карту и выгрузку. Видео подключить к тому же пути обработки кадров после получения формата и способа геопривязки. Если нужно показать интеграцию до готовности модели, использовать явно обозначенный тестовый режим с заранее заданным ответом и отдельно показать проверку реального инференса, когда она доступна.

## 5. Текстовая расшифровка архитектурной схемы

**Компонентная диаграмма.** UI связан с backend. У backend три связи — с компонентом «ИИ», с DB и с файловым хранилищем. На диаграмме последовательности связь с «ИИ/алгоритмом» реализуется через воркер. БД содержит сведения о файлах и результатах. Хранилище содержит сами фото.

**Участники диаграммы последовательности.** Пользователь, Frontend, backend, воркер, ИИ/алгоритм, DB, хранилище данных.

1. Пользователь добавляет фото во frontend.
2. Frontend отправляет фото в backend. Сообщение на рисунке подписано `add_pictures/POST{pictures:binary}`.
3. Backend сохраняет фото в хранилище.
4. Backend сохраняет данные о фото в DB.
5. Backend возвращает frontend сведения о сохранённом объекте загрузки. Frontend сообщает пользователю об успешном сохранении фото.
6. Воркер получает из DB список необработанных фото.
7. Воркер получает фото из файлового хранилища по ID.
8. Воркер отправляет фото на обработку компоненту «ИИ/алгоритм».
9. «ИИ/алгоритм» возвращает воркеру данные обработанного изображения.
10. Воркер обновляет данные изображения в DB.
11. Командный план дополняет последовательность получением результатов из API для таблицы, карты и отчёта.

В успешном ответе на загрузку речь идёт о сохранённом файле. Строки распознавания появляются позже. На схеме указан `add_pictures`, в плане обозначены `/upload`, `/objects`, `/defects`. Контракт в разделе 8 использует `/upload` как рабочий вариант для нового прототипа.

**Предлагаемый вариант фоновой обработки.**

- Храни состояние по файлу и агрегируй прогресс по пакету. Рабочие значения `queued`, `processing`, `completed`, `failed`, в терминологии UI — «В очереди», «Обрабатывается», «Готово», «Ошибка».
- Считай файл принятым после сохранения байтов и записи метаданных. Если запись в БД сорвалась после записи файла, обработай сиротский файл. Если запись уже существует, а исходник потерян, покажи ошибку обработки с идентификатором материала.
- Воркер атомарно закрепляет за собой доступный файл. При нескольких воркерах допустимо использовать выборку с блокировкой строк и короткую транзакцию для захвата задания. Декодирование и инференс выполняются после освобождения блокировки. При восстановлении после падения понадобятся срок владения заданием или явное правило возврата в очередь.
- Сохраняй результат и признак завершения согласованно. Один файл с нулём объектов может иметь `completed`. Ошибка чтения или модели даёт `failed` либо контролируемый повтор. Сбои отдельных файлов видны в пакете независимо от готовности других.
- При повторе одной попытки сохраняй один комплект результатов. В простом варианте одна активная версия результата на файл заменяется транзакционно. Если нужна история, привязывай результат к версии модели и идентификатору прогона, а UI показывает выбранную версию по общему правилу.
- Для MVP достаточно опроса статуса загрузки frontend по API. Период обновления, лимит повторов и уведомления согласуются при реализации. Отдельный брокер очередей имеет смысл, если у команды появится соответствующее требование или потребность.

## 6. ERD и предлагаемая модель данных

### Что изображено на скриншоте ERD

| Таблица | Поля и типы дословно по обозначениям на схеме |
| --- | --- |
| `users` | `id integer` (ключ), `email string`, `phone string`, `username varchar`, `role varchar`, `update_at timestamp`, `created_at timestamp` |
| `infrastructure_objects` | `id integer` (ключ), `imgUrl string`, `type string`, `statusId string`, `place string` |
| `statuses` | `id integer` (ключ), `type string`, `description string` |

Видимая связь проведена между `infrastructure_objects.statusId` и `statuses.id`. У стороны справочника на скриншоте нарисована кратность «ноль или много», у стороны объектов — одинарная черта. Если по смыслу каждому объекту положен один текущий статус из справочника, ожидаемая кардинальность будет обратной — одна запись справочника может использоваться многими объектами. Уточнить обязательность статуса. При внешнем ключе на `statuses.id` согласовать типы, поскольку `statusId` в эскизе строковый, а справочник имеет числовой ключ. Отдельные связи с `users` не показаны. `place` на эскизе — строка, пригодная для адреса или подписи. Построение карты по плану потребует явной модели координат.

Для этапа от загрузки до детекции необходима запись об исходнике. На скриншоте отдельные таблицы файлов, кадров и дефектов отсутствуют, а трекер описывает проектирование ERD с объектами, дефектами, координатами, загрузками и статусами. Смысл `imgUrl` нужно согласовать. Возможный вариант — внешнее представление ссылки на фото, сформированное API из внутреннего ключа файла. Поля `username` и `role` не раскрывают протокол входа. При локальной парольной авторизации понадобится хранение хеша пароля либо отдельный провайдер идентификации. Снимок не указывает ни один из вариантов.

### Предлагаемая гранулярность для нового прототипа

| Сущность | Пример полей и связи |
| --- | --- |
| Пакет загрузки `uploads` | `id`, `created_by → users.id`, `created_at`. Пакет содержит несколько файлов, его состояние удобно вычислять из состояний файлов. |
| Исходный файл `media` | `id`, `upload_id → uploads.id`, `storage_key`, исходное имя, тип фото/видео, MIME, размер, `processing_state`, время загрузки и обработки, безопасный код ошибки. |
| Кадр `frames` | `id`, `media_id → media.id`, ссылка на изображение, ширина, высота, смещение от начала видео в миллисекундах, время съёмки при наличии, место съёмки и источник координат. Для фото создаётся один логический кадр, который может ссылаться на тот же файл. |
| Наблюдение `detections` | `id`, `frame_id → frames.id`, класс объекта, границы области на кадре, уверенность, версия модели, необязательный `object_id → infrastructure_objects.id`. Это обнаружение на одном кадре. |
| Признак `findings` | `id`, `detection_id → detections.id`, код признака, уверенность при наличии, область дефекта при наличии, критичность и рекомендованное действие по согласованным правилам. Одно наблюдение может иметь несколько признаков. |
| Физический объект `infrastructure_objects` | `id`, тип, известный внешний идентификатор при наличии, текстовое место, координаты самого объекта при наличии, ссылка на статус. Один объект может встречаться в нескольких наблюдениях. |
| Справочник `statuses` | `id`, устойчивый тип или код, описание. Значения и бизнес-смысл статуса утверждаются командой. |

Вариант с полным реестром объектов нужен при наличии каталога МГТС или надёжного сопоставления. При запуске только с кадрами MVP может показывать наблюдения как кандидатов, оставляя `object_id = null`. Повторные кадры одного объекта не дают основания считать количество уникальных объектов. При наличии инвентарного идентификатора можно связывать наблюдения через него. Устранение дублей по расстоянию и типу требует собственной проверки на близких объектах. Фото, физический объект, наблюдение и дефект имеют разные идентификаторы. Сохранённое фото может существовать до обработки, а физический объект может существовать в каталоге до загрузки фото.

Для координат можно хранить отдельные `lat/lon` в прикладном контракте и точку SRID 4326 в PostGIS при пространственных запросах. Граница области относится к пикселям кадра. Хранимые даты следует передавать с явным часовым поясом там, где известно абсолютное время. Для видео сохраняется относительное смещение даже при неизвестном абсолютном времени.

## 7. Входные материалы и геопривязка

### Что известно о входе

- Кейс описывает изображения с камер служебных автомобилей. План команды предусматривает фото и видео и разбор GPS из EXIF или JSON.
- Тип и размер файлов, частота кадров, устройство камеры, формат JSON, корректность времени съёмки, наличие трека и инвентарного каталога остаются неизвестными. Поддержку форматов, пределы размера, частоту выборки кадров и приоритет источников определяют по реальному набору.
- При локальном тесте допустимы обычные тестовые фото и отдельные метаданные. У такого примера указать, какие данные синтетические. Фото, на которых виден тип объекта, нужны для проверки детекции. Искусственные координаты проверяют только транспорт данных, карту и отчёт.

### Предлагаемая обработка

1. Принять файл, проверить размер, допустимый тип и возможность декодирования. Для пакетной загрузки сохранять однозначное соответствие между входным файлом, метаданными и ответом API.
2. Для фото получить метаданные до создания уменьшенной копии. Ориентацию нормализовать одинаково для модели и для отображения. Если EXIF содержит геопозицию, перевести её в десятичные градусы с учётом полушария. При отсутствии часового пояса исходное время остаётся локальным или неопределённым до подтверждения.
3. Для видео извлекать кадры с настраиваемым шагом. Хранить временную метку каждого кадра от начала конкретного файла. Абсолютное время связывать с треком только при известных начале записи и правилах синхронизации. Если у одного видео указана единственная координата без привязки ко времени, отмечать её как метаданные видео и выбирать семантику показа отдельно.
4. Для переданных JSON-данных определить, чем они адресуют фото или кадр. Устойчивый идентификатор предпочтителен, а одинаковые имена требуют дополнительного ключа. Для трека согласовать способ поиска точки, допустимый временной разрыв и интерполяцию. Без подтверждённого правила несопоставленные кадры остаются без локации.
5. Сохранить источник геопозиции и вид точности. Названия источников в рабочем варианте — `exif`, `sidecar_json`, `gps_track`, `asset_registry`. Значение `accuracy_m` можно заполнять, когда у источника или метода есть обоснованная оценка. Перечень источников расширяется по фактическим данным.
6. Проверить, что широта и долгота заданы вместе, являются конечными числами и входят в диапазоны ±90 и ±180 градусов соответственно. Для API использовать именованные поля `lat` и `lon`. При построении геометрии `x` — долгота, `y` — широта. Отсутствие значения передаётся через `null`.
7. Если есть достоверная координата самого объекта, показывать её. Иначе при наличии точки съёмки можно показать ориентировочную метку камеры с соответствующей подписью. Если обе точки отсутствуют, показывать запись только в таблице с пометкой «Локация неизвестна». Та же трактовка действует в отчёте.

### Что видит оператор

- **Положение объекта известно.** На карте отображается точка объекта, например из инвентарного справочника. Ссылка на кадр остаётся у наблюдения.
- **Известна только точка съёмки.** Карта и отчёт уточняют «Точка съёмки, положение объекта ориентировочное». Время кадра и источник локации помогают проверить вывод.
- **Координат нет.** Результат распознавания доступен в списке. В отчёте поля координат пустые, статус локации указан отдельно. Текстовый адрес, если он известен, может отображаться отдельно.

Для получения более точной точки объекта можно оценивать сопоставление с реестром, направление движения, параметры камеры или несколько наблюдений только при наличии соответствующих данных. Прямое преобразование пиксельной области в координаты по одной GPS-точке не обосновано.

## 8. Предлагаемый контракт API

В командном плане перечислены `/upload`, `/objects` и `/defects`. Ниже описан согласованный внутри этого файла вариант, с которым можно написать моки, клиент и backend без дополнительных материалов. Роуты, поля, аутентификация и значения перечислений в этом разделе являются предложением. Актуальный контракт определяется командой или существующей реализацией, если пользователь её предоставит.

| Операция | Пример запроса | Что возвращает или делает |
| --- | --- | --- |
| Вход | `POST /auth/login` с `username` и `password` | JWT для защищённых запросов. Ошибка неверных данных входа возвращается без раскрытия внутреннего устройства системы. Если у проекта уже есть провайдер входа, использовать его контракт. |
| Загрузка | `POST /upload`, `multipart/form-data`, повторяемое поле `pictures` и необязательное поле `metadata` | Подтверждение сохранения, идентификатор пакета и результаты по входным файлам. Название `pictures` взято из архитектурного эскиза как отправная точка. Для первой версии поле можно использовать для фото, поддержку видео включить после согласования форматов. |
| Статус пакета | `GET /uploads/{upload_id}` | Список принятых файлов со статусами, прогресс пакета, безопасные коды ошибок. |
| Наблюдения | `GET /objects?upload_id=...&type=...&limit=...&offset=...` | Строки обнаруженных объектов на кадрах. Единица строки — наблюдение с `detection_id` и необязательным `object_id`. |
| Признаки дефектов | `GET /defects?upload_id=...&severity=...&action=...&limit=...&offset=...` | Признаки, связанные с наблюдениями и кадрами. Для таблицы и карты действуют те же правила фильтрации. Карта показывает строки с доступной локацией. |
| Просмотр кадра | `GET /frames/{frame_id}/image` | Исходное изображение или согласованная версия с той же пиксельной системой координат. Контракт доступа к фото следует выбрать вместе с JWT. |
| Отчёт | `GET /defects/export?format=csv&upload_id=...&severity=...&action=...` | Файл CSV или XLSX по выбранным фильтрам. Для выгрузки всего отфильтрованного набора границы страницы UI не применяются. |

Рабочий вариант входного `metadata` для пакета фото — JSON-массив. У элемента есть `file_index`, равный позиции файла в повторяемом поле `pictures` с нуля, и необязательные поля `captured_at`, `lat`, `lon`. Идентификатор позиции включается в ответ, чтобы UI мог сопоставить одинаково названные файлы. Такое соглашение относится к тестовым данным. Формат от МГТС может потребовать отдельного адаптера.

Пример ответа `POST /upload` для одного принятого файла. Вариант HTTP-статуса для постановки в обработку — `202 Accepted`.

```json
{
  "upload_id": 31,
  "items": [
    {
      "file_index": 0,
      "media_id": 101,
      "filename": "demo-01.jpg",
      "processing_state": "queued",
      "error_code": null
    }
  ]
}
```

Строка `GET /defects` ниже иллюстрирует структуру. Данные, координаты, названия классов и значения уверенности в примере условные. Они служат для проверки форматов.

```json
{
  "items": [
    {
      "finding_id": 9001,
      "detection_id": 501,
      "object_id": null,
      "upload_id": 31,
      "media_id": 101,
      "frame_id": 201,
      "image_path": "/frames/201/image",
      "frame_width": 1280,
      "frame_height": 720,
      "object_type": "cable_manhole",
      "object_confidence": 0.91,
      "object_bbox_xyxy": [468, 380, 710, 540],
      "defect_type": "cover_displaced",
      "defect_confidence": 0.84,
      "defect_bbox_xyxy": [504, 414, 678, 503],
      "severity": null,
      "recommended_action": "check",
      "captured_at": "2026-11-17T09:30:00Z",
      "capture_location": { "lat": 55.7500, "lon": 37.6100, "source": "exif" },
      "object_location": null,
      "map_location": { "lat": 55.7500, "lon": 37.6100, "kind": "capture" },
      "model_version": "demo-v1"
    }
  ],
  "total": 1,
  "limit": 50,
  "offset": 0
}
```

Для `GET /objects` использовать тот же формат пагинации, поля наблюдения и связь с кадром. Одно наблюдение может дать несколько строк в `/defects`. Счётчики должны явно различать наблюдения, признаки и уникальные объекты, известные по `object_id`. Если локация отсутствует, `map_location = null`. Если модель не локализует сам дефект, `defect_bbox_xyxy = null`, и интерфейс может показывать область объекта. Границы пиксельных областей передаются в порядке `[x_min, y_min, x_max, y_max]`.

**Правила ошибок для проектирования.** До сохранения возвращать ошибку целого запроса при неверной структуре или превышении общего лимита. Если поддерживается частичный приём, в ответе для каждого непринятого файла возвращать `file_index`, состояние приёма и понятный код причины, а для принятых — `media_id` и `processing_state`. Явно описать, какой HTTP-ответ предусмотрен для пакета, в котором не принято ни одного файла. Ошибки обработки уже принятого медиа отражать в статусе пакета. Примеры причин — `unsupported_media`, `file_too_large`, `decode_failed`, `inference_failed`. Доступ к просмотру фото, результатам и выгрузке проверить теми же правилами авторизации, что и к данным в UI. Для защищённого списка в новом API по умолчанию можно использовать `Authorization: Bearer <token>`.

## 9. CV, датасет и трактовка результата

**План команды.** Собрать и разметить мини-датасет с люками, опорами и дефектами, обучить базовую YOLOv8 или YOLOv11, получить `best.pt` и скрипт инференса. Поставляемые данные и классы ещё нужно подтвердить у организаторов.

**Рабочий план эксперимента.**

1. Просмотреть выборку кадров. Оценить долю целевых объектов, видимость, частоту дефектов и количество разных поездок. Записать классы и инструкцию разметчика с положительными, отрицательными и пограничными примерами.
2. Размечать области целевых объектов и дефектов по выбранной схеме. Для слабовидимых случаев определить правило пропуска или отдельную категорию. Включить кадры без объектов и нормальные объекты, чтобы можно было оценить ложные срабатывания.
3. Разделить обучающие, валидационные и тестовые данные по поездкам или другому независимому признаку. Соседние кадры из одного ролика должны оставаться в одной части. При малом датасете указывать число изображений и примеров по классам, особенно для редких дефектов.
4. Выбрать подход после проверки разметки. Вариант A — одна модель, если классы однозначно кодируют обнаруживаемые объекты и их видимые состояния. Вариант B — детектор объектов плюс модель или правило для состояния области объекта, если признаки нужно оценивать отдельно. В обоих случаях API связывает признак с наблюдением и кадром.
5. Запускать инференс по кадрам с общей схемой ориентации и размеров. Если модель меняет размер входа, привести рамки к системе координат изображения, доступного пользователю. Отдавать список результатов, который может быть пустым, и фактическую версию модели.
6. Настроить пороги по валидационным данным и проверить их на отдельной выборке. Высокая уверенность модели относится к обнаружению паттерна. Критичность и действие выводятся отдельно, если команда согласовала их по признакам и рискам.
7. Сохранять для воспроизведения версию весов, список классов, пороги, размер входа, параметры извлечения кадров, выборку и условия прогона. Скрипт инференса должен уметь обработать один кадр и пакет.

**Ответ CV для воркера.** На входе идентификатор и декодированное изображение или путь к кадру. На выходе версия модели, размеры и список наблюдений. Наблюдение содержит класс, уверенность и рамку объекта, а также ноль или больше признаков с их классом, уверенностью и рамкой, если они рассчитаны. Привязка к пакету, геоданным и пользовательским правам остаётся на стороне приложения. Способ вызова может быть Python-функцией в воркере. Отдельный HTTP-сервис CV — вариант при необходимости независимо обновлять или масштабировать модель.

## 10. Правила формирования перечня и отчёта

В перечне для проверок нужна строка, по которой можно найти кадр и понять причину включения. В рабочем варианте строка соответствует одному видимому признаку. Группировка по объектам возможна, когда есть устойчивый `object_id`. Для простого MVP достаточно вывода найденных признаков как кандидатов на проверку. Правило автоматической рекомендации ремонта, полноценный статус выезда и интеграции с процессами МГТС требуют отдельных данных.

| Понятие | Пример смысла в прототипе |
| --- | --- |
| Статус обработки файла | Техническое состояние работы воркера по файлу. |
| Видимый признак или дефект | Предположение модели или результат проверки, связанный с кадром. |
| Уверенность модели | Число для оценки результата распознавания. |
| Критичность | Приоритет осмотра или действия по согласованным предметным правилам. При отсутствии правила можно оставить значение пустым. |
| Рекомендованное действие | `check` как пример отметки о необходимости проверки. Ремонтные действия — по утверждённой логике. |
| Статус объекта или проверки | Бизнес-состояние, например после осмотра оператором, если команда введёт такой процесс. Значения из ERD ещё не известны. |

В список полезно включать тип объекта, признак, состояние локации, источник, время материала при наличии и ссылку на кадр. Выгрузка по фильтрам включает стабильные ID, эти же поля в машиночитаемом виде, широту и долготу отдельными столбцами, тип точки, критичность и рекомендованное действие. В CSV корректно экранировать разделители, кавычки и переводы строк, использовать кодировку UTF-8 и явно выбрать разделитель. Для открытия в Excel проверить кириллицу и интерпретацию текстовых ячеек. Для XLSX хранить координаты числовыми значениями, а неизвестные поля оставлять пустыми. Имена форматов, столбцов и правила доступа можно согласовать при реализации.

## 11. Интерфейс без макета Figma

**Что было видно в референсе KSYUSHA DB.** Отдельный экран авторизации с небольшим белым блоком по центру светлого фона, заголовком, полями логина и пароля и синей основной кнопкой. Рабочие экраны имеют синюю верхнюю панель с названием и действием выхода справа, белую боковую навигацию со светло-синей подсветкой активного пункта, светло-серый фон и белую рабочую область. Внутри — компактные табличные списки со строками, кнопкой добавления и действиями у записи. Формы добавления и редактирования размещены на отдельной белой панели с полями и основной кнопкой. Демонстрационные сущности и тексты референса относятся к другому домену. Для МГТС использовать компоновку и адаптировать подписи, таблицы и формы под мониторинг.

**Текстовый макет рабочих экранов — предлагаемая адаптация.**

```text
┌──────────────────────────────────────────────────────────────┐
│ Мониторинг инфраструктуры МГТС                       Выйти │
├─────────────────┬────────────────────────────────────────────┤
│ Загрузки        │ Объекты и дефекты                          │
│ Объекты         │ [Тип объекта] [Критичность] [Действие]     │
│ Карта           │ [Скачать отчёт]                           │
│                 │ Фото | Объект | Признак | Локация | ...   │
│                 │ [Открыть кадр и детали выбранной строки]  │
└─────────────────┴────────────────────────────────────────────┘
```

| Экран | Содержание и действия |
| --- | --- |
| Вход | Заголовок системы, поля логина и пароля, кнопка входа, состояние отправки формы, понятное сообщение при ошибке. После входа переход к рабочей области. |
| Загрузки | Выбор одного или нескольких файлов, список выбранных элементов, кнопка отправки. При необходимости — ввод или прикрепление метаданных по согласованному формату. После отправки показать пакет, статус каждого файла, ошибки отдельных элементов и переход к результатам. |
| Объекты и дефекты | Табличный список. Предлагаемые колонки — миниатюра, тип объекта, признак, критичность, рекомендованное действие, местоположение и источник, дата кадра. Объекты без выявленного признака могут оставаться в общем списке. Рабочий список проверок формируется по признакам и правилам действия. |
| Детали результата | Исходное фото или кадр с областью объекта, признаком при наличии, типом, источником координат, временем и статусом. Для рамок изображение должно пересчитываться в фактический размер превью. По возможности показывать место на карте, если координаты доступны. Допустима панель или отдельная страница. |
| Карта | Метки по отфильтрованным результатам, подпись различия между точкой объекта и камеры, открытие сведений и переход к тому же кадру, что в таблице. Карта может пустовать, если у результатов отсутствует точка. В этом случае вывести причину и ссылку на список. |
| Экспорт | Кнопка или меню CSV/XLSX в контексте списка. Пользователю должно быть понятно, по какой выборке выгружается файл. |

Для входа, загрузок и списков предусмотреть нормальные состояния ожидания, ошибки и пустого результата. Сообщения различают «В обработке», «Объекты не найдены», «По фильтрам ничего не найдено» и «Произошёл сбой обработки». Критичность отображается текстом, цвет может её дополнять. На узких экранах навигация может сворачиваться, а таблица — прокручиваться. Набор вкладок и точные надписи в разделе предложены для ориентира.

## 13. Проверка MVP и метрики

### Сценарии приёмки — предлагаемый набор

| Вход или действие | Ожидаемое поведение |
| --- | --- |
| Фото с подтверждённым тестовым признаком и локацией | Файл сохраняется, результат фоновой обработки появляется после обработки. Строка открывает нужный кадр. Запись на карте и в выгрузке относится к тому же результату. |
| Известна только точка съёмки | Метка показывается с подписью об ориентировочной локации. В выгрузке указан тип точки. |
| Целевой объект без выявленного признака | Объект может появиться в списке наблюдений. Запись на проверку формируется только по согласованному правилу. |
| Кадр без объектов | Файл имеет состояние «Готово» и ноль детекций. |
| Кадр с несколькими объектами | У наблюдений собственные ID и рамки. Каждый признак связан с нужным наблюдением. |
| Кадр без GPS | Результат остаётся в таблице с пометкой. Карта пропускает строку, если отсутствует и точка объекта. |
| Кадр из видео с треком | Контрольное смещение соотнесено с ожидаемой точкой. Ссылка ведёт к извлечённому кадру. |
| Смешанный пакет | Валидные и непринятые файлы однозначно сопоставляются с входом по позициям. Состояние обработки валидных файлов видно независимо от ошибок других. |
| Сбой модели, перезапуск воркера | Ошибка видна отдельно от отсутствия объектов. Повтор не умножает комплект результатов. |
| Фильтр и выгрузка | После выбора фильтра таблица и карта согласованы. Отчёт содержит отфильтрованные записи по тем же правилам. Кириллица и координаты читаются корректно. |
| Истёкший или отсутствующий JWT | Защищённый API отклоняет запрос, интерфейс предлагает снова войти. |
| Чистый запуск | Из оговорённого состояния поднимаются БД, API, воркер и UI. Миграции применены, демоданные и наличие весов проверяются отдельно. |

### Что измерить и как представить

- **Качество распознавания.** В плане указана mAP. Написать, какой вариант измерен, например mAP@0.50 или mAP@0.50:0.95, на какой разметке, по каким классам и на каком наборе. Для дефектов при наличии данных полезны полнота, точность и примеры типичных пропусков и ложных срабатываний.
- **Скорость.** FPS относится к ясно описанному этапу. Отдельно можно измерить время инференса и время от приёма файла до выдачи результата. Указать CPU/GPU, модель, размер кадра, число кадров, размер пакета и включены ли декодирование, запись и прогрев.
- **Геопривязка.** Для точности координат объекта нужны контрольные точки объектов. Измерять расстояние в метрах на сопоставленных примерах и указывать размер выборки и долю записей с пригодной локацией. При проверке только EXIF/JSON можно подтвердить корректность переноса координат и происхождение точки. Для сравнения каскадов можно фиксировать медиану и разброс ошибок, если выборка позволяет.
- **Прикладной эффект.** Для демонстрации полезно показать время ручного просмотра и время работы со списком на одном и том же наборе материалов. Полученные величины указывать как измерение только после прогона. Предварительная оценка должна быть помечена отдельно.

В доступных материалах измеренные значения отсутствуют. Для отчёта хранить результаты с датой, набором данных, версией модели, конфигурацией и шагами воспроизведения. Моки, искусственные координаты и демонстрационные подписи проверяют понятность сценария и согласованность компонентов.

## 14. Запуск и демонстрация

**Предлагаемая структура запуска для нового проекта.** В Docker Compose описать PostgreSQL с PostGIS, API, воркер и frontend. Воркер и API используют общую БД и хранилище исходников. Веса модели доступны воркеру по настраиваемому пути. Миграции должны быть применены до использования таблиц сервисами. Пример настроек для описания проекта — строка подключения к БД, корень хранилища, путь к весам, допустимые ограничения загрузки, секрет подписи JWT, адрес API для UI и настройки карты. Имена переменных, порты и значения зависят от реализации. Если внешняя картографическая подложка недоступна на демонстрации, сохранить возможность показать таблицу, локацию и экспорт.

**Предлагаемый порядок демонстрации.**

1. Назвать задачу МГТС, входные данные и рабочий результат в одном предложении.
2. Открыть UI, войти и загрузить небольшой пакет фото. Показать, что сообщение о загрузке появляется до результата обработки.
3. Дождаться готовности, открыть найденный объект и показать кадр с видимым признаком.
4. Открыть соответствующую метку, объяснить источник координат и отличие точки объекта от точки съёмки. Применить фильтр и экспортировать список.
5. Привести реальные измерения или объяснить методику и объём уже проверенного. Показать один характерный пограничный случай и рассказать, как система его отражает.
6. Сформулировать, какие финальные данные от МГТС нужны для проверки устойчивости и практического эффекта.

Для короткой защиты заранее подобрать кадры, на которых видна предметная задача. Подготовить отдельно сквозной демонстрационный сценарий и пояснение технических решений. Если часть возможностей работает на моках, подписать это в демонстрации.

## 15. Правила квалификации и финала

**Квалификация.** Капитан подаёт через платформу один общий текст команды. Крайняя дата — 19 ноября 2026 года, объём — до 2 000 знаков без пробелов. Пять тем ответа — выбор направления, мотивация, понимание задачи и сложности, первоначальный подход, полезные знания и опыт участников. Дополнительные файлы для этого этапа не требуются.

**Оценка квалификации.** За выбор направления и мотивацию, понимание задачи, реалистичность подхода, готовность и компетенции ставят по 0–5 баллов. Максимум — 20. При равных баллах сначала учитывают понимание задачи, затем подход.

**Финал.** Результаты квалификации — 23 ноября. Подтверждение участия и состава — до 24 ноября. Очный финал — 26 ноября 2026 года в МТУСИ, Москва. Детальный кейс и данные выдают в день финала. Основная работа длится до трёх часов. После первой защиты пять команд направления проходят в суперфинал. На финале соответствие задаче весит 20%, техническая обоснованность — 25%, реализуемость — 20%, измеримый эффект — 20%, защита — 15%. Участники лично участвуют в разработке и защите, указывают использованные материалы и компоненты, учитывают ограничения на распространение конфиденциальных материалов. [Положение МГТС, разделы 7–11, 15 и 17](https://lk.studchamp.mgts.ru/storage/docs/regulation.pdf)

В командном плане фигурируют 19 ноября, 23:59, для подачи и 24 ноября для методического вебинара. Точное время подачи и программу финала сверяет капитан в полученных организаторских уведомлениях. В трекере квалификационный ответ описан фразой «пять критериев». При подготовке ответа ориентируйся на пять тем Положения и его шкалу из четырёх критериев. Пять взвешенных критериев действуют на финале.

**Как собрать квалификационный текст.** В одной компактной истории объяснить выбор задачи и мотивацию, назвать основную сложность видимого состояния и геопривязки, изложить цепочку «кадр → детекция → признак → место → перечень», затем привязать реальные компетенции участников к частям решения. Конкретную мотивацию, имена, опыт команды и результаты брать только из сообщения пользователя. Ограничение по длине относится к заявке организатору. Этот контекстный файл предназначен для работы команды и имеет другой объём.
